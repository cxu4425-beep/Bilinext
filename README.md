# BiliNext

**一個自己架來看 bilibili 的第三方客戶端。**
用你自己的帳號登入,關注、收藏、歷史、稍後再看、觀看進度都和官方 App 同步。

登入走**官方 App 掃碼**,密碼不會經過本程式;登入憑證加密存在你自己的電腦上。

```
你的裝置 ──► 你自己的 server (Node) ──► bilibili
瀏覽器 / 手機 APK / Windows        代轉 API、圖片與影音串流
```

## 為什麼需要一台伺服器

bilibili 的 API 與 CDN 會檢查 `Referer`,而瀏覽器**不允許網頁自行偽造 `Referer`**。
所以影片、圖片、API 都必須由一個後端代為轉發 —— 這就是 `server/` 存在的唯一理由。
它同時也負責 WBI 簽章與存放登入憑證。

```
手機 / 桌面 App ──► 你的 server (Node) ──► api.bilibili.com
                        └── 代轉 DASH 影音串流(支援 Range,可拖曳進度)
```

## 快速開始

在專案資料夾**按兩下 `bilinext.cmd`**。第一次會自動安裝相依套件並建置,之後只要幾秒。

那個黑色視窗就是伺服器 —— **用 App 的時候要讓它開著**,關掉視窗就等於關掉伺服器。
它會一次把三種用法都準備好,並印出各自的位址:

```
  --------------------------------------------------------------
  BiliNext is running. Keep this window open.
  --------------------------------------------------------------
  On this computer   http://localhost:8787
  On your Wi-Fi      http://192.168.0.142:8787
  From anywhere      https://fingers-editorial-along-tsunami.trycloudflare.com

  Access key         c56cd3f250474612bde4786652edf0440...
  --------------------------------------------------------------
  Scan with your phone to open the app with the key already filled in:
  [ QR code ]
```

- **區網位址**挑的是有預設閘道的網卡,不會印出 VPN / WSL / Hyper-V 那些手機連不到的虛擬位址。
- **公開網址**需要 cloudflared(`winget install --id Cloudflare.cloudflared -e`);沒裝就只印前兩個,其他照常運作。
- **存取金鑰**第一次執行時產生,存在 `data/access-key`。因為伺服器這時對整個區網開放,而它是登入狀態的,
  所以金鑰一律啟用 —— 詳見[從外面連](#從外面連公開網址)。
- **QR code** 掃了就直接打開 App 並把位址和金鑰填好,不用手打。

或用指令:

```bash
npm install
npm run build
npm start
npm test      # 彈幕行位配置的斷言測試
```

開 <http://localhost:8787>,右上角「登入」→ 用手機 bilibili App 掃碼。

### 開機自動啟動(選用)

重開機後伺服器不會自己回來。若希望登入 Windows 時自動啟動,執行一次:

```
install-autostart.cmd
```

它只會在**你自己帳號**的「啟動」資料夾放一個捷徑(背景執行、不顯示視窗),
隨時可用 `uninstall-autostart.cmd` 移除,不會動到系統其他設定。

### 重複啟動 / 連接埠被占用

兩個啟動檔都會先確認 8787 有沒有人在聽。已經有 server 在跑的話,它只會提示你用現有的那個,
**不會**去搶連接埠。

若是被其他程式占用,server 會印一行說明後以狀態碼 1 結束,不會噴 Node 的堆疊訊息:

```
  Port 8787 is already in use, so BiliNext did not start.
  Most likely it is already running - just open http://localhost:8787
  To use a different port:   set PORT=8788 && npm start
```

(這幾行刻意用英文:純 cmd 主控台預設不是 UTF-8,中文會變亂碼。)

### 伺服器沒開會怎樣

前端是靜態檔並由 Service Worker 快取,所以就算伺服器沒跑,頁面**還是會打開**。
這時介面會顯示一條黃色橫幅說明「連不上本機伺服器」,並且**不會**謊稱你已登出 ——
你的登入憑證還在 `data/` 裡。伺服器一啟動,畫面會在幾秒內自動恢復,不必重新整理。

開發模式(前端熱更新):

```bash
npm run dev
```

## 手機使用

**用相機掃 `bilinext.cmd` 印出來的 QR code。** 就這樣 —— 它會打開 App,位址和金鑰都已經填好。

QR 裡的連結長這樣:

```
https://xxx.trycloudflare.com/#/setup?key=c56cd3f2...
```

金鑰放在 `#` 後面的**片段**是刻意的:片段永遠不會送到伺服器,所以就算頁面是掛在 GitHub Pages 上,
金鑰也只留在手機裡,不會進任何人的存取紀錄。App 讀完會立刻把它從網址列清掉。

手機端有兩種用法:

- **瀏覽器 + 加到主畫面** —— 掃 QR 之後選「加到主畫面」,就是 PWA,有圖示、全螢幕、離線殼層。
- **APK** —— 見下方[打包成安裝檔](#打包成安裝檔)。APK 不能掃 QR,但可以把那行連結整串貼進設定畫面,一樣會自動拆出位址和金鑰。

沒有公開網址(沒裝 cloudflared)時,QR 指的是區網位址,只有同一個 Wi-Fi 連得到。

## 從外面連(公開網址)

想在外面用手機看,而不是只在家裡的 Wi-Fi,需要兩件事:伺服器要有一個 **https** 網址,而且要有**存取金鑰**。

### 為什麼一定要金鑰

這台伺服器已經登入你的 bilibili 帳號,而且沒有任何密碼保護 —— 放到公網上,**拿到網址的人就等於拿到你的帳號**。
所以設了 `BILI_ACCESS_KEY` 之後,每個 `/api` 呼叫都要帶著它才會被受理(健康檢查除外,它要能回答「這個位址對不對、需不需要金鑰」)。

金鑰有兩種傳法,因為**圖片和影片是 `<img>` / `<video>` 在載入的,沒辦法帶 header**:

| 請求 | 金鑰怎麼帶 |
| --- | --- |
| API(fetch / XHR) | `x-bili-key` 標頭 |
| `/api/proxy/image`、`/api/proxy/media` | 網址上的 `?k=`,由伺服器產生連結時自動加上 |

代價是金鑰會出現在圖片網址裡(瀏覽器的網路紀錄看得到)。自用可以接受,但**別把畫面或網址分享出去**。

### 通道

`bilinext.cmd` 只要偵測到 cloudflared 就會自動開一條 Cloudflare quick tunnel,不用另外做什麼。沒裝的話:

```bash
winget install --id Cloudflare.cloudflared -e
```

(裝完要**開新的終端機**,或直接重跑 `bilinext.cmd`,不然 PATH 還是舊的。)

**quick tunnel 的網址每次重開都會變。** 要固定網址得註冊 Cloudflare 帳號建一條具名 tunnel,那是另一套設定。
網址一變,手機上存的舊位址就失效了,重掃一次 QR 即可。

### 從 GitHub Pages 使用

`https://cxu4425-beep.github.io/Bilinext/` 放的是**只有前端**的版本,由 `.github/workflows/pages.yml` 在每次推上 main 時自動建置。

它一樣要連到你的伺服器,而且**只能連 https 的位址** —— Pages 強制 https,瀏覽器禁止 https 頁面呼叫 http,
所以填家裡的 `http://192.168.x.x:8787` 一定會被擋掉,必須用上面的通道網址。

伺服器那邊要允許這個來源(`bilinext.cmd` 已經設好了):

```
set BILI_ALLOWED_ORIGINS=https://cxu4425-beep.github.io
```

這份 build 和瀏覽器版有三個差別:網址前綴是 `/Bilinext/`、用 hash 路由(Pages 沒有 fallback 到 index.html)、
沒有 Service Worker(部署後才不會繼續拿到舊的殼)。

> 說實話:通道網址本身就已經是完整的 App 了(伺服器會把前端一起送出去),同源、不用 CORS、不用把金鑰放進網址。
> Pages 這條路的好處只是網址好記、不會每次變。

## 多使用者(讓別人也能用)

```
bilinext.cmd multi
```

這個模式下,伺服器不再只服務你一個人:

- **每個人掃自己的 QR 登入**,拿到自己的 session token,各自用自己的帳號,互不干涉。
- **沒登入的訪客是匿名的** —— 熱門、搜尋、看影片這些公開內容可以用,需要帳號的部分會提示登入。
  **絕對不會借用你的帳號**(這是刻意的:單人模式下沒有 session 就用預設帳號,多人模式下沒有 session 就是沒有帳號)。
- **session 30 天沒用就失效**,連帶刪掉那個人的 bilibili cookie。`BILI_SESSION_DAYS` 可改。
- **完全開放**:任何人打得開網址就能加入。要踩煞車:`set BILI_MAX_ACCOUNTS=5`(0 = 不限)。

單人模式(不加 `multi`)行為完全不變。

### 實作方式

身分靠 `AsyncLocalStorage` 帶在呼叫堆疊上(`server/src/util/ctx.js`)。這是整件事的關鍵:
`bili/api.js` 有幾十個端點,如果要把「哪個帳號」當參數傳下去,每一個都要改。實際上真正讀 cookie 的只有
`client.js` 的 `currentAccount()` 一個地方,所以只要讓它去問上下文就好,路由幾乎沒動。

| | 怎麼做 |
| --- | --- |
| token 儲存 | 只存 `sha256(token)`,檔案被偷也無法重放 |
| token 傳遞 | API 用 `x-bili-key` 標頭;圖片/影片用網址 `?k=`(元素無法帶標頭) |
| 媒體網址 | 每個人帶**自己的** token,不是共用金鑰 |
| 帳號清單 | 多人模式只回自己那一個;切換帳號直接 403 |
| 登出 | 撤銷該帳號的**所有** session,並刪掉 cookie |
| 續播 / 稍後再看 / 歷史 | 自動變成各自的 —— 它們本來就是照「目前帳號」查的 |

### 你要承擔的

這些不是可以靠寫程式解掉的,只能知道並管理:

- **你保管別人的 bilibili 憑證。** 加密存在 `data/store.enc`,但你的電腦被入侵,就是他們的帳號被盜。
- **大家共用你的 IP。** bilibili 的風控看 IP。一個人被判定異常,**所有人**一起吃 `-352`,他們的帳號也可能被限制。
- **影片全部走你家的上傳頻寬。** 兩三個人同時看就會卡,這點沒有技術解法。
- **你的電腦要一直開著**,而且 quick tunnel 的網址每次重開都變。多人用的話實際上需要具名 tunnel + 一個網域。
- **完全開放代表你不知道會有多少人。** `BILI_MAX_ACCOUNTS` 是唯一的煞車。

## 打包成安裝檔

### Android APK

`android/` 已經產生好了,改完程式碼要重新打包只需要:

```bash
npm run android:apk      # 建置前端 → cap sync → gradlew assembleDebug
```

產物在 `android/app/build/outputs/apk/debug/app-debug.apk`(約 4 MB),把它傳到手機
點開安裝(第一次要允許「安裝未知來源的應用程式」)。

這是 debug build,用 Android 內建的 debug 金鑰簽章 —— 側載自用沒問題,但不能上架,
也無法直接升級成別的金鑰簽的版本。要出正式版得自己產一份 keystore 並設定簽章設定;
`npm run android:aab` 目前產出的是**未簽章**的 bundle。

APK 需要伺服器用 `bilinext.cmd` 啟動(這個模式才對區網和外網開放),否則手機連不到。

需要的工具鏈:JDK 21 與 Android SDK(platform 35、build-tools 35)。
兩者的路徑寫死在 `android/gradle.properties`(`org.gradle.java.home`)和
`android/local.properties`(`sdk.dir`),所以不必設 `JAVA_HOME` / `ANDROID_HOME`;
換機器時改這兩行即可。

`npm run android:open` 則是丟給 Android Studio 開(如果有裝)。

#### 為什麼這個 build 跟網頁版不是同一份

前端有兩種 build,差別由 `vite build --mode capacitor` 決定(`web/.env.capacitor`):

| | 瀏覽器 | APK |
|---|---|---|
| 輸出目錄 | `web/dist` | `web/dist-native` |
| API 位址 | 同源,空字串 | `localStorage` 裡的伺服器位址 |
| 路由 | `BrowserRouter`,網址可分享 | `HashRouter` |
| 資源路徑 | `/assets/...` | `./assets/...` |
| Service Worker | 有(PWA) | 無 |

輸出目錄**一定要分開**:伺服器服務的是 `web/dist`,而 vite 會先清空要寫入的目錄 ——
共用一個的話,打包 APK 會在網站正在被使用時把它清掉,而且結束後留在 `web/dist` 的是
APK 那份(hash 路由、API 位址是空的),等於把網頁版換掉。這個坑實際踩過一次。

會分成兩份,是因為 `capacitor.config.json` 指定 `androidScheme: http`,APK 裡的頁面
是從 `http://localhost` 載入的 —— 執行時跟一般瀏覽器分頁**完全分不出來**,所以只能在
建置時決定。(舊版用 `window.location.protocol === 'capacitor:'` 判斷,那個條件永遠
不會成立。)`HashRouter` 則是因為 APK 裡沒有伺服器可以把 `/video/BV...` fallback 回
`index.html`,重新載入會直接 404。

#### 第一次開啟

APK 內只有前端,所以會先出現設定畫面要你填伺服器位址:

- 在電腦執行 `bilinext.cmd`,把它印在 QR code 上面那行連結整串貼進來,位址和金鑰會自動拆開。
- 或按「自動搜尋」,它會掃常見的家用網段找會回應 `/api/health` 的機器。掃描放在
  按鈕後面而不是自動執行 —— 在別人的網路上打幾百個請求,應該是使用者主動要求的。

之後要改位址,在「設定 → 伺服器位址」。存檔後會自動重載,因為 API base 只在模組
載入時讀一次。

#### Android 專案裡動過的地方

`npx cap add android` 產生的樣板有幾處不能直接用:

- **`network_security_config.xml`** —— Android 從 API 28 起預設擋掉明文 HTTP,而這個
  App 本來就是要連 `http://192.168.x.x:8787`。網路安全設定只能列出具體主機名,沒有
  「我的區網」這種寫法,所以只能整個 App 放行明文。https 的憑證驗證沒有放寬。
- **啟動畫面** —— 樣板的 `AppTheme.NoActionBar` 把 `android:background` 設成 `@null`,
  在啟動畫面消失到第一次繪製之間會閃一下系統的白底。改成和 App 同一個深色,並補上
  Android 12+ 才會讀的 `windowSplashScreenBackground` / `windowSplashScreenAnimatedIcon`。
- **圖示** —— 樣板放的是 Capacitor 的商標。`npm -w web run icons -- --android` 會用
  跟網頁圖示同一份程式碼重畫全部 mipmap;adaptive icon 的前景層直接沿用 maskable 那版
  (108dp 畫布、內容留在中央 72dp 安全區,正好符合)。

### 觀看進度與續播

在 BiliNext 看影片會把進度回報給帳號(`/x/v2/history/report`),所以官方 App 的歷史紀錄看得到、也能從同一個位置接著看;
反過來,官方看到一半的影片點進來會從上次的位置繼續,左下角提示「已從上次看到的 X 繼續播放」並附「從頭播放」。

- 位置來自官方網頁播放器自己用的 `/x/player/wbi/v2`(`last_play_time`、`last_play_cid`),實測和歷史紀錄的 `progress` 一致。
  **只在同一個分 P 續播** —— 位置記在哪個 cid 上就只對那個 cid 有意義。
- 跟 bilibili 一樣:不到 5 秒不續播;停在最後 5 秒內視為看完,從頭開始。
- 回報時機:播放中每 15 秒、暫停、播完、離開影片頁、**App 切到背景**(手機上這是最後一次可靠的機會,之後系統可能直接把 App 殺掉)。
  離開頁面的那次用 `keepalive`,分頁關掉也送得出去。
- 只打開影片、沒有真的播放,**不會**留下紀錄。
- **在讀到帳號上的位置之前,不自動播放,也不回報。** 這是實際踩過的坑:自動播放從 0 秒開始、續播位置晚一點才到,
  這幾秒內離開頁面,就會把「0 秒」回報上去,蓋掉原本的 36 秒。另外,登入檢查還沒完成時,
  `loggedIn` 對所有人都是 false —— 這時若當成「未登入、不續播」,之後真正的位置到了也會被忽略,所以要等 `ready`。
- 換分 P、換畫質時,位置是在 `<video>` 的 `emptied` 事件裡送出的。這個事件排在元素被歸零之前,
  若改在之後才讀 `currentTime`,送出去的會是「新分 P 的 0 秒」,等於把上一 P 的進度洗掉。

### 稍後再看

側欄(手機在「我的」頁)有「稍後再看」,影片頁的反應列也有同名按鈕可以加入/移除。
有個 API 的時間差要注意:寫入立刻回 `code 0`,但**清單要過幾秒才反映**
(實測加入後馬上讀,`count` 還是舊的;刪除後馬上讀,影片還在)。所以按鈕與清單都**以寫入結果為準**,不在寫入後重新讀取 ——
否則按鈕會自己跳回原本的狀態。

### 手機手勢

只對觸控生效,滑鼠操作完全不變:

| 手勢 | 動作 |
|---|---|
| 點一下 | 顯示/隱藏控制列 |
| 點兩下 | 左 1/3 倒退 10 秒、右 1/3 快轉 10 秒、中間播放/暫停 |
| 左右滑 | 拖動進度(整個寬度 = 2 分鐘,短片則為整部),放開才跳轉 |
| 上下滑(僅全螢幕) | 左半邊亮度、右半邊音量 |

幾個刻意的取捨:

- **點一下不暫停。** 暫停改用點兩下中間;否則每次想叫出控制列都會打斷影片。
- **上下滑只在全螢幕有效。** 一般頁面裡播放器下面還有留言,播放器若吃掉上下滑,整頁會滑不動;
  所以非全螢幕時 `touch-action: pan-y` 把垂直滑動交還給瀏覽器捲動。
- **亮度是畫面亮度,不是螢幕亮度。** 網頁沒有權限調系統亮度,這裡是把影片畫面調暗(最低 20%),離開全螢幕自動恢復。
- **音量是播放器音量。** 手機實體音量鍵照常控制系統音量。
- 控制列隱藏時不接收點擊,第一下點擊一定是叫出控制列,不會按到看不見的按鈕。

點進影片會自動播放(可在「設定 → 播放」關閉)。這件事有個瀏覽器層面的坑值得記著:

bilibili 的 DASH 影片軌**不含聲音**,所以瀏覽器把 `<video>` 當成靜音元素,不需要使用者手勢就會播;
但另一個 `<audio>` 元素沒有這個豁免。天真地自動播放的結果是**畫面在動、卻沒有聲音** —— 比不播還糟。
因此程式會分辨兩種 `play()` 失敗:

- `NotAllowedError` = 瀏覽器真的擋了 → 畫面照播,左上角顯示「點擊開啟聲音」
- `AbortError` = **我們自己**中斷的(影片卡頓時 `onWaiting` 會暫停音訊,這會中止還在進行中的 `play()`)
  → 忽略。把這個誤判成被擋,會在聲音明明正常的影片上蓋一個提示

從站內點進影片時,那次點擊本身就是瀏覽器要的手勢,所以聲音正常;
直接開網址或重新整理則沒有手勢,會維持封面與播放鍵,不會假裝在播。

版面有兩種模式,用播放列上的「寬螢幕」鈕切換,選擇會記住:

- **一般**(預設,同原版):播放器靠左,相關推薦在右側與播放器同高並排
- **寬螢幕**:播放器橫跨整個寬度,資訊與推薦排在下方

彈幕資料來自 bilibili 官方客戶端使用的 **protobuf 分段介面**(`/x/v2/dm/web/seg.so`,每段 6 分鐘),
解碼器在 `server/src/bili/dmproto.js`,不需任何套件。舊的 XML 介面(`list.so`)只是**取樣**:
它自己宣告 `maxlimit=500`,在一部 2:24 的影片上只回 600 則,分段介面則回 4,823 則 —— 這就是彈幕看起來稀疏的原因。
XML 只在分段介面失敗時當備援。進階彈幕(mode 7/8/9)是腳本而非文字,不會被當成捲動彈幕顯示。

畫面塞滿時,預設讓彈幕**重疊**(與原版相同),放到碰撞最少的那一行;不再把排不進去的丟掉。
不喜歡重疊可在播放列齒輪裡勾「防止重疊」。

彈幕採 bilibili 原本的 SimHei 字體堆疊,**不加粗**(SimHei 只有一個字重,要求 bold 會讓瀏覽器合成加粗,看起來比原版明顯厚),外框粗細隨字級等比縮放。
字級依串流中每則彈幕自帶的數值渲染,並且**每一幀重新換算**,所以進出全螢幕時畫面上既有的彈幕會一起縮放,不會出現大小不一。
大小的算法照 bilibili:**固定 CSS 像素**(25px × 字體大小設定),不隨播放器高度縮放。
先前是隨高度等比縮放,在一般大小的視窗裡比官方小約 1.5 倍。只有兩個例外:播放器很小(手機、窄視窗)時等比縮小,
全螢幕時**字體維持和視窗模式一樣大**,多出來的高度用來放更多行彈幕;想要全螢幕等比放大,可在齒輪裡開「全螢幕同步縮放」(預設關閉,不從帳號同步)。

字體大小、不透明度、顯示區域**預設取自帳號同步的彈幕設定**(`/x/v2/dm/web/view` 回應的第 10 欄),
所以一開始就和官方客戶端一樣;在 BiliNext 裡手動改過任何一項後,就改以這裡的設定為準。
欄位是拿官方客戶端本機存的設定逐一對過的:11 不透明度、12 區域、13 速度、14 字體大小、15 全螢幕同步。
預設鋪滿整個畫面,可在播放列的齒輪調整顯示區域、不透明度與字體大小。暫停時只有一個淡出的圖示動畫,不會把畫面壓暗。

滑鼠移到單一彈幕上會浮出工具列(讚 / 複製 / 檢舉),與原版相同:

- 命中判定在畫布上做,但畫布維持 `pointer-events: none`,所以永遠不會吃掉本來要點影片的滑鼠事件
- 被指到的那則彈幕會**暫停移動**並轉白;工具列打開後**游標離開也不會消失**,
  要點影片空白處、按 Esc 或拖動進度才會關閉,而關閉用的那一下點擊不會順便暫停影片
- 按讚數不在彈幕串流裡,是用彈幕 id(`p` 屬性的第 7 欄)向 `/x/v2/dm/thumbup/stats` 單獨查的,
  只查游標指到的那一則,不會為了 1800 則彈幕預先拉一次
- 檢舉會先跳確認,因為送出後收不回來

置頂(mode 5)與置底(mode 4)彈幕各有獨立的行位,捲動彈幕會避開置頂佔用的行。
這段行位配置抽成純函式 `web/src/lib/danmakuLanes.ts` 並有測試(`npm test`)—— 它壞掉時不會拋錯,只會安靜地把字疊在一起,所以值得用斷言守住。

關注頁左側是 UP 主側欄,做法與原版一致:資料取自 bilibili 動態頁自己用的
`/x/polymer/web-dynamic/v1/portal`,所以**排序(最近有更新的在前)、未讀紅點、正在直播的標記**
都與官方站一致,不是自己推算的。手機版會變成頂部的頭像橫向捲動列。

動態本身是單欄卡片流(不是影片格狀清單),與原版一致:

- **標頭**:頭像、藍色使用者名稱、`47分鐘前 · 投稿了視頻`(動作文字直接取自 API 的 `pub_action`)
- **內文**:富文本節點分別渲染 —— 話題 `#...#` 與 `@提及` 是藍色可點、行內表情是圖片。
  若只取 `desc.text` 這些全部會退化成純文字
- **主體**:影片(封面 + 時長 + 標題 + 播放/彈幕)、圖片(單張保留比例、多張變方格)、直播卡
- **轉發**:原文嵌在較深色的內凹面板裡,標示 `@原作者`;若你沒關注對方會出現「+ 關注」鈕
- **頁尾**:轉發 / 留言 / 讚,三個都是可按的:
  - **讚** —— 即時更新數字,失敗會回滾
  - **留言** —— 就地展開留言串。動態的留言區型別各不相同(影片 `1`、圖文 `11`、轉發 `17`),
    程式讀 `basic.comment_id_str` 與 `comment_type`,三種型別都實測拉得到真實留言
  - **轉發** —— 展開輸入框,可附一段話

右側是「關注直播」面板,資料同樣來自 portal(頭像、直播中標記、直播標題),沒人開台時整塊隱藏。

轉發卡的「+ 關注」依據 `module_author.following` 顯示。這是個沒有文件的列舉,我對著實際的關注清單驗過:
`1` = 已關注、`2` = 未關注(feed 中 8 位 `following=2` 的作者全都不在關注清單內,而關注清單裡的人全是 `1`)。

## 視覺風格的來源

配色與尺度不是憑印象調的,是從**桌面版 bilibili 客戶端本身**讀出來的。
它是 Electron 應用,用 `--remote-debugging-port` 啟動後可以直接把它的 CSS 變數表撈出來
(共 988 個 token),再取深色模式下實際解析出的值。

兩個容易做錯、而這個專案原本也做錯的地方:

- **它的灰是中性灰**(`#17181A`),不帶藍。原本用的是偏藍的 `#0f1117`,
  即使強調色調對了,整體仍然「不像」。
- **品牌粉在深色模式會降飽和**:`#FF6699` → `#D44E7D`。
  把亮粉直接放在深色底上會刺眼,官方並不是那樣出貨的。

| | 官方值(深色) |
| --- | --- |
| 背景 | bg1 `#17181A` / bg2 `#101011` / bg3 `#0A0B0C` |
| 文字 | text1 `#E7E9EB` / text2 `#A2A7AE` / text3 `#757A81` |
| 分隔線 | `#232527` / `#2F3134` / `#46494D` |
| 品牌 | 粉 `#D44E7D`、藍 `#0087BD`、連結 `#58B1D4` |
| 圓角 | 4 / **6(卡片)** / 8 / 10 |
| 間距 | 5 / 10 / 15 / 20 / 25 / 30 |
| 字級 | 24 / 18 / 16 / 14 / 13 / 12,行高 1 / 1.25 / 1.5 |

版面尺寸同樣是量出來的:首頁四欄、卡片內容 304px、封面 16:9 圓角 6px、
封面到文字 10px、列距 40px;動態頁 UP 側欄 260px(列高 52px)、動態流 595px。

只取設計語言(顏色、圓角、字級、間距、版面比例),沒有複製任何官方圖檔或圖示。

## 安全性設計

- **不碰密碼。** 只有掃碼登入一條路,本程式僅取得掃碼後產生的 cookie。
- **憑證加密存放。** `data/store.enc` 以 AES-256-GCM 加密,金鑰在 `data/key`(權限 0600),或用 `BILI_STORE_KEY` 環境變數提供。
- **阻擋跨站寫入。** 所有寫入 API 都要求自訂標頭 `x-bili-client`,瀏覽器無法在跨來源請求中夾帶它,因此你開著的其他網頁無法透過 localhost 操作你的帳號。
- **代理有白名單。** 只轉發 bilibili 自家網域,不會變成公開的開放代理。
- **圖片只取縮圖。** 頭像與封面都改抓 hdslb 的裁切版本(`@96w_96h_1c.webp` 等)。有些使用者的頭像其實是 2048×2048、數 MB 的裝扮大圖,直接抓原圖既慢又會裁得亂七八糟。
- **投稿需明確確認。** 送出投稿的 API 必須帶 `confirm: true`,前端也要求勾選同意。

要完全清除登入狀態:在介面上登出,再刪掉 `data/` 目錄。

## 已知限制

這些是真話,不是免責條款:

- **依賴非公開 API。** bilibili 隨時可以改。改了之後對應功能會壞,需要更新程式碼。`/x/web-interface/view` 已經因為反爬蟲擋在 412,目前改用需 WBI 簽章的 `wbi/view` 版本 —— 這類事情還會再發生。
- **點踩(`archive/dislike`)是整組反應中最不穩的。** bilibili 把它當推薦回饋而非公開計數,路徑變動過。失敗時介面會直接報錯,不會假裝成功。
- **第三方投稿風險最高。** 上傳流程完整實作且可跑,但這是最容易觸發風控的操作。用它之前請自行評估。
- **觀看進度回報與稍後再看的加入/移除已用真實帳號實測**(只動到自己的觀看資料,且測試時送的是帳號原本就有的進度)。
- **多使用者模式只用一個帳號驗證過。** 匿名訪客、session 隔離、帳號清單、切換被擋、登出撤銷都實測過,
  但「兩個不同的人同時在線」沒有真的試過(需要第二個 bilibili 帳號)。
- **手機手勢沒有在實機上測過。** 邏輯與型別都已檢查,但實際手感(滑動靈敏度、點兩下的判定時間 280ms)需要在手機上確認。
- **其餘寫入操作仍未實測。** 按讚/點踩/投幣/收藏/留言/發彈幕/投稿/投票這些**寫入**路徑是照官方網頁的請求格式實作的,尚未真的送出過。所有**讀取**路徑都已用真實帳號實測通過:首頁、搜尋、影片、播放、彈幕、留言、關注(169 人)、收藏夾(4 自建 + 2 收藏,含內容)、我的投稿(9 部)、歷史、動態、私訊、提醒。
- **私訊只支援純文字。** 圖片與卡片訊息會顯示為「非文字訊息」。
- **「我是否已投票」是推斷出來的。** `vote_info` 沒有明確的欄位,程式把回應中與 `info` 平行的 `status` 當成自己的選項編號(0 = 未投票)。這點未經實測驗證(驗證需要真的投票,而投票不可撤銷)。為保險起見,本次投票的選擇也會存到瀏覽器的 localStorage,即使 `status` 不如預期,投完票後畫面仍會正確顯示結果。複選投票的 `status` 表示方式未知。
- **個人空間投稿列表(`space/wbi/arc/search`)是風控最嚴的讀取端點。** 它需要一整組裝置指紋參數(`dm_img_str` 等)才會回應,程式已經帶上。**登入後穩定可用**;未登入且短時間連續呼叫仍會被擋。遇到 `-352` 時伺服器會自動重建裝置識別(buvid)後重試一次,再失敗就回 HTTP 429。
- **請求頻繁可能被風控。** 伺服器會把 `-352` 與反爬蟲的 412 HTML 頁面統一轉成 HTTP 429 並在介面提示,但最好的做法還是別把它當爬蟲用。
